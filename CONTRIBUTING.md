# Contributing

## Layout

- `templates/` holds template packages, grouped by kind, such as `code/go`.
- `policies/check/` holds policy packages for `weaver registry check`.
- `diagnostic_templates/` renders policy findings as JSON for the policy tests.
- `buildscripts/` holds the test harness that the mise tasks call.
- `.config/mise/tasks/` holds the mise tasks.

## Adding a template package

Create a directory under `templates/{kind}/{name}` with:

- `weaver.yaml`, declaring every param with a default that works for any
  registry.
- The `*.j2` templates.
- `README.md`, covering usage, output, params, and stability.
- `tests/{case}/registry/`, a registry that exercises the package.
- `tests/{case}/params.yaml`, when the case overrides params.
- `tests/{case}/expected/`, the output the case must produce.
- `tests/{case}/expected-error.txt` in place of `expected/`, when the case
  must fail generation. It holds text that one of the diagnostics contains.

Generate `expected/` with `mise run weaver:test:update`, then read every file it
wrote before committing it.

## Adding a policy package

Create a directory under `policies/check/{name}` with:

- One or more `*.rego` files. Findings about a metric or other signal set
  `signal_type` and `signal_name`.
- `README.md`, listing each finding ID and what triggers it.
- `tests/{case}/current/`, the registry to check.
- `tests/{case}/base/`, a baseline registry, when the policy compares versions.
- `tests/{case}/expected-diagnostic-output.json`, generated by
  `mise run weaver:test:update`.

Include a case that produces no findings and a case for each finding ID.

## Testing

Tools are pinned in [`mise.toml`](mise.toml). With [mise](https://mise.jdx.dev)
installed:

```bash
mise install
mise run weaver:test
mise run markdown:check
```

Run `mise tasks` to list every task and what it does.

Every test must pass before a pull request is merged. The `Checks` workflow
runs the same tasks.

Keep test registries synthetic. Use neutral namespaces such as `myapp` and
`auth` rather than conventions from a real system.

## Pull requests

Pull request titles follow
[Conventional Commits](https://www.conventionalcommits.org), because they become
the squash commit and drive the changelog:

- `feat: ...` for a new package or capability.
- `fix: ...` for a bug fix.
- `chore: ...` for anything that does not change a package.

Add `!` after the type, as in `feat!: ...`, for a change that breaks consumers,
such as renaming a param or a generated identifier. Before 1.0.0 a breaking
change bumps the minor version and anything else bumps the patch version.

## Releases

[release-please](https://github.com/googleapis/release-please) keeps a release
pull request open with the next version and changelog. Merging it tags
`v{version}` and publishes the release. Do not edit `CHANGELOG.md` by hand.
